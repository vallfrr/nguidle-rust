# Vita 60 Hz: scripted sessions, traces and the optimization loop

Goal: constant 60 Hz presentation on the PS Vita at the lowest clocks that hold it, with the game logic unchanged.
Method: replay the same real play session automatically, record every frame, let a script say where the time goes.
Nothing here needs a person (or a model) in the loop: one command per measurement, one short report per run.

## Pieces
| Piece | What it does |
| --- | --- |
| `clr/src/autoplay.rs` | Scenario reader. Injects the console's own inputs (`ngu_pad`, touch through `ngu_frame`, `ngu_scroll`) at given **simulation ticks** (30 per game second, independent of the frame rate, so a slow frame never reorders the session). Also the PC runner `clr <dll> autoplay <assets> <scenario> <trace.csv>`. |
| `clr/src/capi.rs` | `ngu_autoplay_load(path)`, `ngu_frame_info(out)` (tick, simulation steps, interpreted instructions, menu id, last action number, mark number, finished flag), `profile_report(top)`. |
| `nguidle-vita/scenarios/*.txt` | Generated by `tools/gen-scenarios.py` (deterministic, public, no game content): `tour` (all 58 menus, 5 s each, ~5 min), `session` (new game, 5 laps over 17 menus with buttons, D-pad, taps, stick, Save page, a save digest per lap, ~30 min), `monkey` (seeded random walk, 2 h). |
| `nguidle-vita/main.c` (benchmark build) | If `ux0:data/ngu/bench/scenario.txt` exists: loads it and writes `bench/trace.bin` (64 bytes per frame, written in chunks by a worker thread) then `bench/done.txt`. |
| `tools/vita-trace.py` | Summary of a trace (`.bin` from the console or `.csv` from PC): work per frame, presentation rate and late frames, worst phases, worst spikes with the scenario line that preceded them, spike periodicity, comparison with a saved baseline. |
| `tools/ngu-profile.sh <scenario>` (WSL) | PC replay + the trace summary + the top methods by exclusive interpreted instructions (hardware independent: what to optimize or translate to Rust). |
| `tools/vita-cycle.sh <scenario> [label]` (WSL) | Build, install if changed, upload, launch, wait for `done.txt`, download, analyze: the whole console measurement. |
| `tools/vita-batch.sh label:scenario[:VAR=val] ...` | Several cycles in a row, one comparison table at the end (overnight runs). |

## Scenario format (`clr/src/autoplay.rs`)
One event per line: `<tick> pad <chars>` (`u d l r` focus, `a` confirm, `b` back, `p n` previous/next menu, one per frame),
`touch <x> <y>`, `scroll <dx> <dy>`, `menu <n>`, `click <label text>`, `mark <name>`, `check <name>`, `shot` (console: bench/shotN.tga, converted by `tools/tga2png.py`), `ui` (debug: screen as text in the log), `end`.
`click` finds the visible control by its label, like the dev mode. A click with no matching control is logged (`[autoplay] click: no control`), not fatal.

## Trace record (16 little-endian u32)
`frame, t_us, work_us (no vsync wait), logic, layout, emit, draw, swap, upload, tick, steps, instr, menu, action, marks, flags`
(flags: 1 = scanout repeat seen, 2 = texture/atlas upload in the frame, 4 = scenario finished). Header `NGUT` + a count the host does not rewrite
(readers use the file size). `t_us` differences give the real presentation cadence: a gap above ~25 ms is a missed refresh.

## Commands
```sh
# PC, hardware independent (WSL): where the interpreted work goes
tools/ngu-profile.sh nguidle-vita/scenarios/tour.txt 20
# console, one run (needs VITA_AGENT, the Vita SDK, the data pack on the console)
tools/vita-cycle.sh session baseline          # then: cp out/vita-60/baseline/summary.json out/vita-60/baseline.json
# console, several variants unattended
tools/vita-batch.sh base:session fast:session:NGU_VITA_FAST_CLOCKS=ON monkey:monkey
```
A late-game measurement needs the late-game save: `FIXTURE=/path/NGUSaveSteam.txt tools/vita-cycle.sh tour late-tour`
(the benchmark build uses `bench/save` as its save folder).

## Rules for the optimization loop
1. Never optimize without a trace that names the cost. Read the short report; open raw files only when the verdict is bad.
2. One change set per measurement cycle; keep it only if p99 or late frames improve and the digests (`check`) do not change.
3. `tools/regress.sh` must stay `ALL OK`. Save digests are only comparable between runs with the same clock and save folder
   (the game stamps real time into a save), so compare them PC-to-PC with `NGU_FIXED_NOW` and Vita-to-Vita.

## What the measurements said (console, 444/222 MHz, fresh game, `session` scenario, 31,450 ticks)
| | before (baseline) | after the changes below |
| --- | --- | --- |
| presented rate | 52.6 fps | 56.5 fps |
| frames later than 25 ms | 9.8 % | 4.1 % |
| frames whose CPU work exceeds 16.7 ms | 39.5 % | 16.7 % |
| work per frame p50 / p99 | 15.3 / 54.6 ms | 10.2 / 37.6 ms |

Findings that drove the work (all from the trace, not guessed):
- One simulation step costs ~11 ms on the Vita for ~15 k interpreted instructions (~1.4 M instructions per second: the interpreter is
  ~50x slower there than on a PC). The layout, draw list and submission add ~7 ms to every frame. At 30 Hz steps on 60 Hz frames this is
  ~60 % of the CPU on average, but a frame that did both could take 18-25 ms.
- Every menu switch ran ~400 k interpreted instructions (`updateBonuses` x 11, 1,144 `specBonus`, 9,152 `equipSpecBonus` calls): 100-250 ms hitch.
- Every 15 steps (0.5 s) the whole scene was laid out again (24 ms on the Vita) because an item icon swapped between two sprites
  of the same size.

Changes (each one checked: `tools/regress.sh` ALL OK, and the save digests of the whole `session` equal with and without them):
1. **Native `equipSpecBonus` / `specBonus`** (`clr/src/vm.rs`, guards 20 and 21): same f32 arithmetic and order as the IL, falls back to the
   interpreter on anything unexpected. A menu switch now costs 93 k instructions instead of 400 k.
2. **Time-sliced steps** (`Vm::frame_start` / `frame_run`, `clr/src/capi.rs`): a step runs over one or two display frames, cut between two
   `Update` components, with the same callback order. The budget is planned from the measured cost of a step and of a redraw
   (`NGU_FRAME_MS`, default 12 ms; `NGU_SLICE_MS`, default 12 on the Vita, 0 = off elsewhere). Discrete input (press, release, pad action, stick)
   completes the step first, and the layout only runs between steps, so the game state does not depend on where a step was cut
   (verified at a 0.05 ms budget, which cuts every step into hundreds of slices).
3. **No redraw on unchanged frames**: when no step completed and nothing was touched, the host draws the previous list again.
4. **`active_in_hierarchy` cached per epoch** (bumped by `SetActive`, destruction, re-parenting): it was 11 % of a step.
5. **No relayout for a sprite swap of the same size** (`Image.set_sprite`): the layout reads only a sprite's size.

Tried and dropped: translating only the hottest classes to Rust (`ngu-ilgen` with a class list). Generated code and the interpreter keep
objects in different representations (Rust structs vs VM objects), so a partial build cannot call back into untranslated methods without
copying every object; not worth the risk. The generator now includes the nested lambda classes of a selected class, which is correct
but unused.

## Two cores: logic and presentation (Vita host, `nguidle-vita/main.c`)
The remaining misses were all the same shape: one thread did input, simulation, layout, draw list, texture upload and presentation, so any slow
stage delayed the refresh. The host now runs two threads:
- **L** (the big-stack `ngu` thread, user core 1): input, `ngu_frame`, `ngu_emit`; copies the finished list into a slot and publishes it
  through a lock-free triple buffer (`ngu_emit_seq()` tells it when the engine built a new list). Paced at ~60 iterations per second.
- **R** (`ngu-render`, user core 0, 512 KiB stack): owns the GL context. Each iteration takes the newest slot, uploads queued textures, draws, and
  presents with vsync, whatever L is doing. A long simulation step no longer delays a refresh; it only delays the next new list.
- Textures and the glyph atlas are copied by L (the engine's RAM copy is freed at once) and uploaded by R; a sprite still in flight is skipped for a frame or two.
- The keyboard dialog lives on R; requests and results go through a small mailbox. Log lines go to a worker thread.
- Time slicing is off by default on the Vita now (`NGU_SLICE_MS=0`): the simulation has a core of its own.
Findings that only the per-frame trace could show (each fixed after one measurement):
1. A synchronous log append every 5 s took ~80 ms (now asynchronous).
2. `glTexSubImage2D` on a texture in use costs ~65 ms per call whatever the size (strips made it worse); every atlas update now goes into a fresh
   texture object that replaces the old one (18 ms for 4 MB).
3. `mallinfo` costs ~5 ms (benchmark statistics only).
Priority note: `sceKernelCreateThread` rejects priority 0x10000080 (ILLEGAL_PRIORITY); user core 2 is refused, cores 0 and 1 work.

| console, 444/222 MHz | single thread (before) | two threads |
| --- | --- | --- |
| `session` (fresh game, 31,450 ticks): presented rate | 56.5 fps | **59.9 fps** |
| frames later than 25 ms | 4.1 % | **1 of 63,064** |
| longest gap after boot | 190+ ms | 30 ms |
| `tour` (58 menus) | 59.2 fps / 152 late | 59.9 fps / 2 late |
| `late` (advanced save, Load Autosave, 58 menus) | n/a | 59.9 fps / 3 late, longest 39 ms |
Screens were checked by eye with the `look` scenario (screenshots of 18 menus: sprites, text and the Save page draw correctly).
What is not fixed: the simulation side still has hitches (a menu switch costs ~65 ms of interpreted work, 150-370 ms for the first visit of some
screens such as Cooking, ~600 k instructions in `getOptimalScore`). The picture keeps refreshing at 60 Hz during them, but a button press
can be answered 4-20 frames late. The `work` columns of the report now describe the slowest stage (L or R) of each presented frame.

## Still open
- Responsiveness of the simulation: menu switches (~65 ms), first visits (up to ~370 ms), the autosave snapshot (~34 M native instructions on L). The picture
  stays at 60 Hz meanwhile. Candidates: fewer redundant `updateBonuses` calls per switch, caching `CookingController` scores, a native or cached
  autosave snapshot. Measure with the `tour` / `late` scenarios and `tools/ngu-profile.sh` (hardware independent).
- A 2-hour `monkey` run and a 30-minute `session` run on the two-thread build; `late` only covered the tour so far.
- Pre-warming glyphs of neighbour screens (first-visit rasterization runs on L now, so it no longer delays a refresh).
- A clock governor (lowest clocks that keep 60 Hz) is now realistic: R needs ~4 ms per frame.

## What a VPK cache can and cannot do (soak analysis)
The sh3/sh4 ports ship a compiled GPU-program cache because they compile shaders at run time. This port uses vitaGL's fixed pipeline with no shaders
of its own, so that cache has no equivalent here. In the 2-hour soak trace the frames over 25 ms are not upload frames (median upload 2 us):
72 % of them spend more than 60 % of their time in game logic, and about 70 % of the frames over 100 ms follow a menu switch
(~95 k interpreted instructions, ~65 ms on the console; the top contributors are `updateBonuses` x 11 and `updateEquipmentBonus`, ~35 k instructions together).
Glyph and texture pre-warming therefore addresses only the first-visit part. Memoizing the inventory bonus loops would save at most ~25 ms per switch
and needs the interpreter to prove the inventory unchanged; not done. Autosave file writing, MD5 and the slot record are already on a worker thread
on the Vita; what remains on the game thread is the snapshot itself. `byte[]` to `Vec<u8>` conversions in `ToBase64String` / stream natives no longer clone
the element vector first (identical output, `tools/regress.sh` ALL OK).

## Status
- Verified on PC: scenario parsing (unit test), the replays, the analyzer, the instruction profile, `tools/guard-check.sh` (guards on/off) and the
  slicing identity check (`NGU_SLICE_MS` 0 / 0.05 / 3), `tools/regress.sh`.
- Verified on the console: the whole loop (`vita-cycle.sh`) with the `tour`, `session` scenarios; numbers above. The 2-hour `monkey` soak (random walk, 389,500 frames,
  216,016 ticks) completed without a crash or a stuck screen: 54.1 fps presented, 6.1 % of frames later than 25 ms, work p50 11.4 / p99 58.6 ms,
  26.8 % of frames over 16.7 ms. Worst gaps: boot (2.9 s), the first click on "Create New Game" (1.0 s), then a few 0.4-0.9 s menu switches.
  Spikes recur about every 27 ticks (~0.9 s), so the remaining cost is spread over many steps, not only the autosave. The monkey
  visits every screen with random input, which is a harder mix than the `session` scenario above.
- Same 2-hour `monkey` soak on the two-thread build: 431,842 frames, no crash or stuck screen, 59.9 fps presented, 4 frames later than 25 ms (longest gap 40 ms).
  Simulation work is unchanged (p99 60.8 ms, worst menu switch 641 ms), so input response can still lag while the picture stays smooth.
- Console cycle pitfalls found: the agent skips an upload whose content it already sent (the scenario gets a unique comment line each time);
  `fs trash` is asynchronous (the scenario file is never trashed); a scripted run never opens the system keyboard (it blocked the console once).
